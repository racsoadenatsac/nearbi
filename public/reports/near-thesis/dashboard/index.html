Is NEAR Intents volume a leading indicator of real usage?

We tested it on 104 weeks of on-chain data. Neither Intents activity nor the NEAR price leads real-user growth. Intents grew while NEAR's own user base shrank: it measures a different population.

Real users (signers plus relayed end users, minus accounts with 1,000+ actions a week) were dominated by one app: KaiChing sub-accounts were 82.9% of all account-weeks and disappeared in April 2026; outside KaiChing, weekly real users fell from 3,699,019 to 284,872 (92.3% lower).

-- name: s1_tx_accounts  (HEAVY, run once)
-- One row per (ISO week, signing account): how many transactions it signed that
-- week, how many of them went straight to intents.near, and on how many days it was active.
-- Columns read: block_date, signer_account_id, receiver_account_id (no args/payloads).
-- window: 2024-10-28 .. 2026-10-25 = 104 full ISO weeks (Monday .. Sunday)
CREATE OR REPLACE TABLE `{stage}.s1_tx_accounts` AS
SELECT
  DATE_TRUNC(block_date, ISOWEEK)            AS week,
  signer_account_id                          AS account_id,
  COUNT(*)                                   AS n_tx,
  COUNTIF(receiver_account_id = 'intents.near') AS n_tx_to_intents,
  COUNT(DISTINCT block_date)                 AS active_days
FROM `bigquery-public-data.crypto_near_mainnet_us.transactions`
WHERE block_date BETWEEN '2024-10-28' AND '2026-10-25'
GROUP BY week, account_id
stage/s2_receipt_roles.sql
-- name: s2_receipt_roles  (HEAVY, run once)
-- From receipt-level actions, two things in a single scan:
--   role 'relayed_user'   : DELEGATE_ACTION rows (is_delegate_action = TRUE). On NEAR a
--                           meta-transaction's delegate receipt is addressed to the end
--                           user (receiver); signer/predecessor are the relayer. So the
--                           relayed end user is receipt_receiver_account_id.
--   role 'intents_action' : every action executed on intents.near (all callers: solvers,
--                           relayers, users, token contracts forwarding deposits).
-- Columns read: block_date, is_delegate_action, receipt_receiver_account_id.
-- window: 2024-10-28 .. 2026-10-25 = 104 full ISO weeks
CREATE OR REPLACE TABLE `{stage}.s2_receipt_roles` AS
SELECT
  DATE_TRUNC(block_date, ISOWEEK) AS week,
  IF(is_delegate_action, 'relayed_user', 'intents_action') AS role,
  receipt_receiver_account_id     AS account_id,
  COUNT(*)                        AS n_actions,
  COUNT(DISTINCT block_date)      AS active_days
FROM `bigquery-public-data.crypto_near_mainnet_us.receipt_actions`
WHERE block_date BETWEEN '2024-10-28' AND '2026-10-25'
  AND (is_delegate_action OR receipt_receiver_account_id = 'intents.near')
GROUP BY week, role, account_id
stage/s5_relayed_gapfill.sql
-- name: s5_relayed_gapfill  (HEAVY, run once)
-- Data-quality fix found by probe p7: before late February 2025 the public dataset has
-- DELEGATE_ACTION rows whose is_delegate_action flag is FALSE (on 2025-01-15 every one of
-- them; on 2025-03-15 flag and action_kind agree exactly). s2 keys on the flag, so it
-- misses relayed users in the early weeks. This table re-derives relayed end users from
-- action_kind = 'DELEGATE_ACTION' for the first 18 ISO weeks (through the week in which the
-- flag starts). q1 takes relayed users from s5 for weeks <= 2025-02-24 and from s2 after,
-- so no week is counted from both tables.
-- Columns read: block_date, action_kind, receipt_receiver_account_id.
-- window: 2024-10-28 .. 2025-03-02 (18 ISO weeks)
CREATE OR REPLACE TABLE `{stage}.s5_relayed_gapfill` AS
SELECT
  DATE_TRUNC(block_date, ISOWEEK) AS week,
  receipt_receiver_account_id     AS account_id,
  COUNT(*)                        AS n_actions,
  COUNT(DISTINCT block_date)      AS active_days
FROM `bigquery-public-data.crypto_near_mainnet_us.receipt_actions`
WHERE block_date BETWEEN '2024-10-28' AND '2025-03-02'
  AND action_kind = 'DELEGATE_ACTION'
GROUP BY week, account_id

-- name: q1_weekly_usage
-- question: Per ISO week, how many accounts used NEAR, split by account family, and how
--           many of them look like real users rather than automation?
-- reads: {stage}.s1_tx_accounts (tx signers), {stage}.s2_receipt_roles (relayed end users
--        + actions on intents.near) and {stage}.s5_relayed_gapfill (relayed end users for
--        the weeks before the dataset's is_delegate_action flag is populated). s2 is ~60 GB,
--        so it is read ONCE, here.
-- relayed source: s5 (action_kind = DELEGATE_ACTION) for weeks <= 2025-02-24, s2 (flag)
--        from 2025-03-03; flagged_relayed_week shows what the flag alone would give.
-- definitions (per week, per account):
--   signer        signed >= 1 transaction
--   relayed       was the end user of >= 1 meta-transaction (DELEGATE_ACTION receiver)
--   users_any     signer OR relayed (distinct accounts; an account counted once)
--   heavy         >= 1000 signed tx + relayed actions in the week (relayers, solvers, bots)
--   users_real    users_any minus heavy
--   users_engaged users_real active on >= 2 distinct days of the week
--   new_users     users_real whose first appearance in the 104-week window is this week
--   retained      users_real that were also active (signer or relayed) the previous week
-- family: account-name pattern (implicit 64-hex, EVM-style 0x, *.tg = HOT, *.sweat = Sweat,
--         *.users.kaiching = KaiChing app sub-accounts (largest relayed suffix, probe p6),
--         other *.near, other). Families partition accounts, so totals = sum over families.
-- fp_*: order-independent content fingerprints of the stage rows read (detects drift).
-- window: 2024-10-28 .. 2026-10-25 (104 ISO weeks)
WITH tx AS (
  SELECT week, account_id, n_tx, n_tx_to_intents, active_days,
         FARM_FINGERPRINT(FORMAT('%t|%s|%d|%d|%d', week, account_id, n_tx, n_tx_to_intents, active_days)) AS fp
  FROM `{stage}.s1_tx_accounts`
  WHERE week BETWEEN '2024-10-28' AND '2026-10-25'
), s2 AS (
  SELECT week, role, account_id, n_actions, active_days,
         FARM_FINGERPRINT(FORMAT('%t|%s|%s|%d|%d', week, role, account_id, n_actions, active_days)) AS fp
  FROM `{stage}.s2_receipt_roles`
  WHERE week BETWEEN '2024-10-28' AND '2026-10-25'
), s5 AS (
  SELECT week, account_id, n_actions, active_days,
         FARM_FINGERPRINT(FORMAT('%t|%s|%d|%d', week, account_id, n_actions, active_days)) AS fp
  FROM `{stage}.s5_relayed_gapfill`
  WHERE week BETWEEN '2024-10-28' AND '2025-02-24'
), intents AS (
  SELECT week,
         SUM(IF(role = 'intents_action', n_actions, 0)) AS intents_actions,
         COUNTIF(role = 'relayed_user')                 AS flagged_relayed,
         BIT_XOR(fp)                                    AS fp_s2
  FROM s2 GROUP BY week
), rel AS (
  SELECT week, account_id, n_actions, active_days, fp FROM s2
  WHERE role = 'relayed_user' AND week >= '2025-03-03'
  UNION ALL
  SELECT week, account_id, n_actions, active_days, fp FROM s5
), acct AS (
  SELECT
    week,
    COALESCE(tx.account_id, rel.account_id)               AS account_id,
    tx.account_id IS NOT NULL                             AS is_signer,
    rel.account_id IS NOT NULL                            AS is_relayed,
    IFNULL(tx.n_tx, 0)                                    AS n_tx,
    IFNULL(tx.n_tx_to_intents, 0)                         AS n_tx_to_intents,
    IFNULL(rel.n_actions, 0)                              AS n_relayed,
    GREATEST(IFNULL(tx.active_days, 0), IFNULL(rel.active_days, 0)) AS days,
    tx.fp AS fp_tx, rel.fp AS fp_rel
  FROM tx FULL OUTER JOIN rel USING (week, account_id)
), first_seen AS (
  SELECT account_id, MIN(week) AS first_week FROM acct
  WHERE n_tx + n_relayed < 1000 GROUP BY account_id
), labeled AS (
  SELECT a.*, f.first_week,
    LAG(a.week) OVER (PARTITION BY a.account_id ORDER BY a.week) = DATE_SUB(a.week, INTERVAL 7 DAY) AS was_active_prev,
    a.n_tx + a.n_relayed >= 1000 AS heavy,
    CASE
      WHEN REGEXP_CONTAINS(a.account_id, r'^[0-9a-f]{64}$') THEN 'implicit'
      WHEN STARTS_WITH(a.account_id, '0x')                 THEN 'evm_0x'
      WHEN ENDS_WITH(a.account_id, '.tg')                  THEN 'hot_tg'
      WHEN ENDS_WITH(a.account_id, '.sweat')               THEN 'sweat'
      WHEN REGEXP_CONTAINS(a.account_id, r'\.users\.(preprod-)?kaiching(\.near)?$') THEN 'kaiching'
      WHEN ENDS_WITH(a.account_id, '.near')                THEN 'named_near'
      ELSE 'other'
    END AS family
  FROM acct a LEFT JOIN first_seen f USING (account_id)
)
SELECT
  l.week,
  l.family,
  COUNT(*)                                                    AS users_any,
  COUNTIF(is_signer)                                          AS signers,
  COUNTIF(is_relayed)                                         AS relayed_users,
  COUNTIF(is_signer AND is_relayed)                           AS signer_and_relayed,
  COUNTIF(heavy)                                              AS heavy_accounts,
  COUNTIF(NOT heavy)                                          AS users_real,
  COUNTIF(NOT heavy AND days >= 2)                            AS users_engaged,
  COUNTIF(NOT heavy AND first_week = l.week)                  AS new_users,
  COUNTIF(NOT heavy AND IFNULL(was_active_prev, FALSE))       AS retained,
  SUM(n_tx)                                                   AS tx_signed,
  SUM(n_relayed)                                              AS relayed_actions,
  COUNTIF(n_tx_to_intents > 0)                                AS intents_tx_signers,
  COUNTIF(n_tx_to_intents > 0 AND NOT heavy)                  AS intents_tx_signers_real,
  SUM(n_tx_to_intents)                                        AS intents_tx,
  ANY_VALUE(i.intents_actions)                                AS intents_actions_week,
  ANY_VALUE(i.flagged_relayed)                                AS flagged_relayed_week,
  BIT_XOR(fp_tx)                                              AS fp_tx,
  BIT_XOR(fp_rel)                                             AS fp_rel,
  ANY_VALUE(i.fp_s2)                                          AS fp_s2_week
FROM labeled l LEFT JOIN intents i USING (week)
GROUP BY l.week, l.family

-- name: s3_intents_token_flows  (HEAVY, run once)
-- Fungible-token (NEP-141) balance changes of the intents.near account, per week.
-- Cross-chain assets on NEAR Intents are the PoA-bridge tokens *.omft.near (one per
-- source-chain asset). ft_events is clustered on contract_account_id, so the scan is
-- pruned with STARTS_WITH on the chain prefixes seen in a 24-day sample, then filtered
-- exactly with ENDS_WITH('.omft.near'). Prefixes not in the list are missed (see THESIS.md).
-- direction: 'in' = intents.near balance increased, 'out' = decreased (burn = bridge-out).
-- Amounts are raw integer token units (no decimals, no prices).
-- window: 2024-10-28 .. 2026-10-25 = 104 full ISO weeks
CREATE OR REPLACE TABLE `{stage}.s3_intents_token_flows` AS
SELECT
  DATE_TRUNC(block_date, ISOWEEK)                          AS week,
  contract_account_id                                      AS token,
  cause,
  IF(STARTS_WITH(delta_amount, '-'), 'out', 'in')          AS direction,
  involved_account_id                                      AS counterparty,
  COUNT(*)                                                 AS n_events,
  SUM(ABS(CAST(delta_amount AS BIGNUMERIC)))               AS raw_amount
FROM `bigquery-public-data.crypto_near_mainnet_us.ft_events`
WHERE block_date BETWEEN '2024-10-28' AND '2026-10-25'
  AND affected_account_id = 'intents.near'
  AND ENDS_WITH(contract_account_id, '.omft.near')
  AND (   STARTS_WITH(contract_account_id, 'eth')   OR STARTS_WITH(contract_account_id, 'base')
       OR STARTS_WITH(contract_account_id, 'sol')   OR STARTS_WITH(contract_account_id, 'gnosis')
       OR STARTS_WITH(contract_account_id, 'arb')   OR STARTS_WITH(contract_account_id, 'hood')
       OR STARTS_WITH(contract_account_id, 'sui')   OR STARTS_WITH(contract_account_id, 'aptos')
       OR STARTS_WITH(contract_account_id, 'aleo')  OR STARTS_WITH(contract_account_id, 'tron')

       OR STARTS_WITH(contract_account_id, 'xrp')   OR STARTS_WITH(contract_account_id, 'ltc')
       OR STARTS_WITH(contract_account_id, 'qtc')   OR STARTS_WITH(contract_account_id, 'doge')

       OR STARTS_WITH(contract_account_id, 'ton')   OR STARTS_WITH(contract_account_id, 'stellar'))
GROUP BY week, token, cause, direction, counterparty

-- name: q2_intents_flows
-- question: Per ISO week, how many cross-chain (PoA-bridge *.omft.near) token movements
--           touched intents.near, in which direction, and from how many counterparties?
-- reads: {stage}.s3_intents_token_flows (tiny). chain = asset prefix before '-' or '.'
--        (eth, sol, btc, tron, ...). Burns (cause ft_burn) are withdrawals back to the
--        source chain. Amounts stay in raw token units (no decimals, no prices).
-- window: 2024-10-28 .. 2026-10-25
SELECT
  week,
  REGEXP_EXTRACT(token, r'^([a-z0-9]+)')                  AS chain,
  COUNT(DISTINCT token)                                   AS tokens,
  SUM(IF(direction = 'in', n_events, 0))                  AS events_in,
  SUM(IF(direction = 'out', n_events, 0))                 AS events_out,
  SUM(IF(cause = 'ft_burn', n_events, 0))                 AS events_burn,
  COUNT(DISTINCT IF(direction = 'in', counterparty, NULL)) AS counterparties_in,
  BIT_XOR(FARM_FINGERPRINT(FORMAT('%t|%s|%s|%s|%s|%d|%t', week, token, cause, direction,
          IFNULL(counterparty, ''), n_events, raw_amount)))  AS fp
FROM `{stage}.s3_intents_token_flows`
WHERE week BETWEEN '2024-10-28' AND '2026-10-25'
GROUP BY week, chain

analysis.py
"""Thesis model: is NEAR Intents cross-chain activity a better leading indicator of real
network usage than the NEAR price?

Run by `run.py analyze` (and re-run by `verify-cached`) inside the rs-repro image with
ROOT (the pack) and OUT (where derived CSVs go). Inputs are only results/q*.csv (weekly
aggregates from BigQuery) and raw/near_usdt_weekly.json (public price series). Pure
pandas/numpy, no randomness, fixed rounding -> byte-identical outputs.

Outputs (OUT/):
  a_weekly.csv     the 104-week panel: levels and weekly log growth of every series
  a_xcorr.csv      lead/lag cross-correlations, lags -8..+8, with n and a 95% band
  a_oos.csv        out-of-sample test: AR(1) baseline vs AR(1) + lagged indicator
  a_families.csv   real users by account family, per week (for the stacked chart)
  a_chains.csv     cross-chain events by source chain, whole window
  a_nep245.csv     sampled-day NEP-245 ledger accounts next to same-week Intents signers
  a_facts.csv      every number quoted in THESIS.md / the dashboard, as displayed
"""
import json
from pathlib import Path

import numpy as np
import pandas as pd

ROOT = Path(globals().get("ROOT", Path(__file__).resolve().parent))
OUT = Path(globals().get("OUT", ROOT / "results"))
R = ROOT / "results"

# ---- parameters (also declared in THESIS.md front matter) ---------------------------
WEEKS = 104                 # 2024-10-28 .. 2026-10-25
LAGS = range(-8, 9)         # k > 0: indicator leads usage by k weeks
FIT_END = "2026-02-22"      # first 69 weeks (~16 months) fit, last 35 weeks (~8 months) test
BREAK = 0.5                 # |weekly log growth| above this marks a regime-break week
Z95 = 1.96

# ---- load ----------------------------------------------------------------------------
q1 = pd.read_csv(R / "q1_weekly_usage.csv")
q2 = pd.read_csv(R / "q2_intents_flows.csv")
q3 = pd.read_csv(R / "q3_nep245_sample.csv")
kl = json.loads((ROOT / "raw" / "near_usdt_weekly.json").read_text())

if isinstance(kl, list):        # Binance klines: [open_ms, open, high, low, close, ...]
    price = pd.DataFrame({"week": pd.to_datetime([k[0] for k in kl], unit="ms").strftime("%Y-%m-%d"),

def xcorr(x, y, k):
    """corr(x[t-k], y[t]); k > 0 means x leads y."""
    a = pd.concat([x.shift(k), y], axis=1).dropna()
    n = len(a)
    if n < 10:
        return np.nan, np.nan, n
    # Spearman = Pearson on average ranks (no scipy in the image)
    rx, ry = a.iloc[:, 0].rank(), a.iloc[:, 1].rank()
    return a.iloc[:, 0].corr(a.iloc[:, 1]), rx.corr(ry), n

-- name: q1_weekly_usage
-- question: Per ISO week, how many accounts used NEAR, split by account family, and how
--           many of them look like real users rather than automation?
-- reads: {stage}.s1_tx_accounts (tx signers), {stage}.s2_receipt_roles (relayed end users
--        + actions on intents.near) and {stage}.s5_relayed_gapfill (relayed end users for
--        the weeks before the dataset's is_delegate_action flag is populated). s2 is ~60 GB,
--        so it is read ONCE, here.
-- relayed source: s5 (action_kind = DELEGATE_ACTION) for weeks <= 2025-02-24, s2 (flag)
--        from 2025-03-03; flagged_relayed_week shows what the flag alone would give.
-- definitions (per week, per account):
--   signer        signed >= 1 transaction
--   relayed       was the end user of >= 1 meta-transaction (DELEGATE_ACTION receiver)
--   users_any     signer OR relayed (distinct accounts; an account counted once)
--   heavy         >= 1000 signed tx + relayed actions in the week (relayers, solvers, bots)
--   users_real    users_any minus heavy
--   users_engaged users_real active on >= 2 distinct days of the week
--   new_users     users_real whose first appearance in the 104-week window is this week
--   retained      users_real that were also active (signer or relayed) the previous week
-- family: account-name pattern (implicit 64-hex, EVM-style 0x, *.tg = HOT, *.sweat = Sweat,
--         *.users.kaiching = KaiChing app sub-accounts (largest relayed suffix, probe p6),
--         other *.near, other). Families partition accounts, so totals = sum over families.
-- fp_*: order-independent content fingerprints of the stage rows read (detects drift).
-- window: 2024-10-28 .. 2026-10-25 (104 ISO weeks)
WITH tx AS (
  SELECT week, account_id, n_tx, n_tx_to_intents, active_days,
         FARM_FINGERPRINT(FORMAT('%t|%s|%d|%d|%d', week, account_id, n_tx, n_tx_to_intents, active_days)) AS fp
  FROM `{stage}.s1_tx_accounts`
  WHERE week BETWEEN '2024-10-28' AND '2026-10-25'
), s2 AS (
  SELECT week, role, account_id, n_actions, active_days,
         FARM_FINGERPRINT(FORMAT('%t|%s|%s|%d|%d', week, role, account_id, n_actions, active_days)) AS fp
  FROM `{stage}.s2_receipt_roles`
  WHERE week BETWEEN '2024-10-28' AND '2026-10-25'
), s5 AS (
  SELECT week, account_id, n_actions, active_days,
         FARM_FINGERPRINT(FORMAT('%t|%s|%d|%d', week, account_id, n_actions, active_days)) AS fp
  FROM `{stage}.s5_relayed_gapfill`
  WHERE week BETWEEN '2024-10-28' AND '2025-02-24'
), intents AS (
  SELECT week,
         SUM(IF(role = 'intents_action', n_actions, 0)) AS intents_actions,
         COUNTIF(role = 'relayed_user')                 AS flagged_relayed,
         BIT_XOR(fp)                                    AS fp_s2
  FROM s2 GROUP BY week
), rel AS (
  SELECT week, account_id, n_actions, active_days, fp FROM s2
  WHERE role = 'relayed_user' AND week >= '2025-03-03'
  UNION ALL
  SELECT week, account_id, n_actions, active_days, fp FROM s5
), acct AS (
  SELECT
    week,
    COALESCE(tx.account_id, rel.account_id)               AS account_id,
    tx.account_id IS NOT NULL                             AS is_signer,
    rel.account_id IS NOT NULL                            AS is_relayed,
    IFNULL(tx.n_tx, 0)                                    AS n_tx,
    IFNULL(tx.n_tx_to_intents, 0)                         AS n_tx_to_intents,
    IFNULL(rel.n_actions, 0)                              AS n_relayed,
    GREATEST(IFNULL(tx.active_days, 0), IFNULL(rel.active_days, 0)) AS days,
    tx.fp AS fp_tx, rel.fp AS fp_rel
  FROM tx FULL OUTER JOIN rel USING (week, account_id)
), first_seen AS (
  SELECT account_id, MIN(week) AS first_week FROM acct
  WHERE n_tx + n_relayed < 1000 GROUP BY account_id
), labeled AS (
  SELECT a.*, f.first_week,
    LAG(a.week) OVER (PARTITION BY a.account_id ORDER BY a.week) = DATE_SUB(a.week, INTERVAL 7 DAY) AS was_active_prev,
    a.n_tx + a.n_relayed >= 1000 AS heavy,
    CASE
      WHEN REGEXP_CONTAINS(a.account_id, r'^[0-9a-f]{64}$') THEN 'implicit'
      WHEN STARTS_WITH(a.account_id, '0x')                 THEN 'evm_0x'
      WHEN ENDS_WITH(a.account_id, '.tg')                  THEN 'hot_tg'
      WHEN ENDS_WITH(a.account_id, '.sweat')               THEN 'sweat'
      WHEN REGEXP_CONTAINS(a.account_id, r'\.users\.(preprod-)?kaiching(\.near)?$') THEN 'kaiching'
      WHEN ENDS_WITH(a.account_id, '.near')                THEN 'named_near'
      ELSE 'other'
    END AS family
  FROM acct a LEFT JOIN first_seen f USING (account_id)
)
SELECT
  l.week,
  l.family,
  COUNT(*)                                                    AS users_any,
  COUNTIF(is_signer)                                          AS signers,
  COUNTIF(is_relayed)                                         AS relayed_users,
  COUNTIF(is_signer AND is_relayed)                           AS signer_and_relayed,
  COUNTIF(heavy)                                              AS heavy_accounts,
  COUNTIF(NOT heavy)                                          AS users_real,
  COUNTIF(NOT heavy AND days >= 2)                            AS users_engaged,
  COUNTIF(NOT heavy AND first_week = l.week)                  AS new_users,
  COUNTIF(NOT heavy AND IFNULL(was_active_prev, FALSE))       AS retained,
  SUM(n_tx)                                                   AS tx_signed,
  SUM(n_relayed)                                              AS relayed_actions,
  COUNTIF(n_tx_to_intents > 0)                                AS intents_tx_signers,
  COUNTIF(n_tx_to_intents > 0 AND NOT heavy)                  AS intents_tx_signers_real,

-- name: s3_intents_token_flows  (HEAVY, run once)
-- Fungible-token (NEP-141) balance changes of the intents.near account, per week.
-- Cross-chain assets on NEAR Intents are the PoA-bridge tokens *.omft.near (one per
-- source-chain asset). ft_events is clustered on contract_account_id, so the scan is
-- pruned with STARTS_WITH on the chain prefixes seen in a 24-day sample, then filtered
-- exactly with ENDS_WITH('.omft.near'). Prefixes not in the list are missed (see THESIS.md).
-- direction: 'in' = intents.near balance increased, 'out' = decreased (burn = bridge-out).
-- Amounts are raw integer token units (no decimals, no prices).
-- window: 2024-10-28 .. 2026-10-25 = 104 full ISO weeks
CREATE OR REPLACE TABLE `{stage}.s3_intents_token_flows` AS
SELECT
  DATE_TRUNC(block_date, ISOWEEK)                          AS week,
  contract_account_id                                      AS token,
  cause,
  IF(STARTS_WITH(delta_amount, '-'), 'out', 'in')          AS direction,
  involved_account_id                                      AS counterparty,
  COUNT(*)                                                 AS n_events,
  SUM(ABS(CAST(delta_amount AS BIGNUMERIC)))               AS raw_amount
FROM `bigquery-public-data.crypto_near_mainnet_us.ft_events`
WHERE block_date BETWEEN '2024-10-28' AND '2026-10-25'
  AND affected_account_id = 'intents.near'
  AND ENDS_WITH(contract_account_id, '.omft.near')
  AND (   STARTS_WITH(contract_account_id, 'eth')   OR STARTS_WITH(contract_account_id, 'base')
       OR STARTS_WITH(contract_account_id, 'sol')   OR STARTS_WITH(contract_account_id, 'gnosis')

-- name: q2_intents_flows
-- question: Per ISO week, how many cross-chain (PoA-bridge *.omft.near) token movements
--           touched intents.near, in which direction, and from how many counterparties?
-- reads: {stage}.s3_intents_token_flows (tiny). chain = asset prefix before '-' or '.'
--        (eth, sol, btc, tron, ...). Burns (cause ft_burn) are withdrawals back to the
--        source chain. Amounts stay in raw token units (no decimals, no prices).
-- window: 2024-10-28 .. 2026-10-25
SELECT
  week,
  REGEXP_EXTRACT(token, r'^([a-z0-9]+)')                  AS chain,
  COUNT(DISTINCT token)                                   AS tokens,
  SUM(IF(direction = 'in', n_events, 0))                  AS events_in,
  SUM(IF(direction = 'out', n_events, 0))                 AS events_out,
  SUM(IF(cause = 'ft_burn', n_events, 0))                 AS events_burn,
  COUNT(DISTINCT IF(direction = 'in', counterparty, NULL)) AS counterparties_in,
  BIT_XOR(FARM_FINGERPRINT(FORMAT('%t|%s|%s|%s|%s|%d|%t', week, token, cause, direction,
          IFNULL(counterparty, ''), n_events, raw_amount)))  AS fp
FROM `{stage}.s3_intents_token_flows`
WHERE week BETWEEN '2024-10-28' AND '2026-10-25'
GROUP BY week, chain
